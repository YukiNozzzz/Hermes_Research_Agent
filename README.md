# 项目研究助手：Hermes MVP

状态：Windows CLI MVP 已实现并通过本机真实验收；Linux 服务器部署与微信接入尚未完成。更新日期：2026-10-26。

**使用入口见 [MVP 快速开始](QUICKSTART.md)，实际测试结果见 [验收记录](VALIDATION.md)。下文保留功能设计和验收目标，不代表所有部署项已自动完成。**

**当前实施依据：[Profile 与聊天渠道实施计划](IMPLEMENTATION_PLAN.md)。已确定一人一个 Hermes profile，项目共享内容存于 profile 外，未来聊天软件按可信账号绑定路由。实际开发以该文档 M0–M5 为准。**

本文替代此前以“单轮 idea 生成”为中心的结构草案，当前范围为每日论文更新、项目记忆与问题探索，并从第一版支持多用户隔离与共享。
独立 Deep Research 入口暂缓，作为后续扩展，不纳入 MVP 的实现与验收。
实现采用 Hermes 插件、两份 Skill、分范围 SQLite 记录与 Markdown / JSON 研究报告；由现有 Hermes 执行模型推理和原生调度。

具体目录、每个文件的职责和调用关系见 [项目结构说明](PROJECT_STRUCTURE.md)。对应功能源码已创建。

## 1. MVP 的目标

围绕一个研究项目，支持多个用户在各自独立的会话中使用，让用户能够：

1. 每日固定时间获得与课题相关的新论文。
2. 换一个会话，Agent 仍能知道项目目标、已有工作、关键决定和现存问题。
3. 针对具体难点主动发起问题探索，得到有依据的候选解释、idea 和验证建议。
4. 将研究结果、用户反馈和实验结果持续回流到项目，供下一轮使用。
5. 在明确权限下共享项目知识，同时隔离各用户的会话、个人记忆和私有研究。

第一版成功的标准是这些能力互相连接，形成可追溯的研究循环，而不是先追求生成质量或全自动科研。

## 2. 范围与初始边界

| 第一版包含 | 后续优化 |
| --- | --- |
| 一个项目、多用户、个人会话与项目共享记录 | 多项目、复杂团队角色与细粒度指定人员共享 |
| 每用户一个专用 profile，额外服务 profile 执行项目级任务 | 更多聊天软件与实际微信收发 |
| 可信用户身份、项目成员关系、私有 / 项目共享范围 | 组织层级、复杂审批与跨组织协作 |
| 一个论文来源，优先 arXiv | 更多论文来源与内部资料渠道 |
| 固定时间自动拉取论文，可手动补跑 | 自适应订阅、复杂优先级策略 |
| 项目背景、问题、进展和决定的维护 | 更复杂的长期记忆管理 |
| 一个研究入口：针对具体问题进行探索 | 独立 Deep Research、多种研究策略和专家角色 |
| 研究结果与依据保存、人工反馈回流 | 自动实验、自动写论文与投稿 |
| 可选：每日更新后触发指定问题探索 | 完全自主安排研究议程 |
| 在现有 Hermes 中使用 | 独立界面、团队平台 |

本机已配置课题“人设对话领域如何对齐用户偏好”和每天 10:00（Asia/Shanghai）的论文更新任务。初次更新读取近期论文摘要，默认最多 10 篇，并明确记录截断情况；本地资料导入支持受控目录中的 Markdown / TXT。
模型探索默认由用户主动触发，每日更新默认只抓取论文。历史实验、个人经验和资源约束仍需用户补充。

## 3. 框架分层

    用户 A → profile A / 用户 B → profile B
      │ 可信渠道绑定、原生 profile 路由、成员关系检查
      ▼
    项目 Agent：每次仅加载该用户在当前项目可访问的上下文
      │
      ├─ 项目记忆与问题清单
      │    目标 / 已有工作 / 决策 / 实验 / 经验 / 待解决问题
      │
      └─ 问题探索
           回顾尝试 → 分析难点 → 定向查资料 → 候选假设 → 质疑与修订
                        │
                        ▼
                 研究结果回流
           更新问题、证据、候选与进展，保留来源
                        │
                        ▼
                  下一次对话 / 研究

    每日论文更新 ──→ 新资料与变化记录 ──→ 项目问答 / 问题探索
                           └─→ 可选：触发已允许自动研究的问题

这些是逻辑职责，不预先要求每一部分都是独立 Agent。
项目 Agent 复用现有 Hermes；由用户专用 profile 管理原生会话。共享记录经插件访问，研究执行方式在对应阶段落实。
复用插件源码不等于共用用户运行状态；个人上下文、历史会话和执行权限必须按用户隔离。
共享项目记录通过明确发布流转，不通过把多个人的聊天历史混入同一个会话实现。

## 4. 六个模块及职责

### A. 项目记忆

维护项目的持续背景：

- 研究方向、目标、成功标准和资源约束。
- 已做的工作、方案、关键决定及理由。
- 实验结果、失败经历和个人经验。
- 当前进展、未解决问题与下一步。
- 指向原始资料、研究任务和对话来源的关联。

项目概览用于快速了解全貌，详细依据按需读取。
不能仅靠一段长期追加的聊天摘要承担全部项目记忆。
项目共享概览只由共享记录组成；用户个人视图可额外结合该用户自己的私有记录。
不能先把所有用户内容汇成总摘要，再尝试隐藏其中的敏感段落。

项目事实、用户经验、Agent 假设、用户决策和实验结果应当区分。
用户已明确表达的决定按其指示记录；Agent 的建议不能自动升级成用户决定。
结论冲突时保留双方的时间、条件与依据，不能静默覆盖旧记录。

### B. 问题清单

每个问题至少能够回答：

- 具体是什么问题，为什么值得解决？
- 相关现象、证据、约束是什么？
- 已尝试什么，结果怎样？
- 当前缺少哪类知识或实验？
- 下一步准备调查、讨论或验证什么？

问题可以处于待处理、研究中、等待外部信息、待验证、已解决或搁置状态。
一个问题可以关联多次调查、多个 idea 和多次实验。
研究结束不等于问题解决；“已解决”需要有明确依据或用户判断。

### C. 每日论文更新

输入：项目课题、订阅条件、时间范围和执行时间。

流程：

1. 固定时间拉取论文；同一流程也可手动执行。
2. 识别新增材料，避免重复处理同一版本。
3. 做初步相关性筛选。
4. 尝试关联已有问题或研究方向；不确定时标记待判断。
5. 记录新增内容、可能影响和本次更新状态。

产物：本轮更新记录、相关论文清单、关联的问题和未完成项。
没有新论文是正常结果；来源访问失败必须与“没有新增”区分。
漏跑或失败后可以补拉；拉取成功与后续研究成功分别记录。

默认只更新资料。是否伴随自动研究，由项目设置决定。

### D. 问题探索

输入：一个具体问题、项目背景、相关历史尝试、用户约束，以及可选的新材料。

流程：

1. 明确本次要推进的难点，以及希望得到解释、方案还是实验建议。
2. 回顾已有工作、失败原因和历史 idea，避免从零开始。
3. 围绕难点检索和阅读相关材料，按需进行有限的定向补查；资料不足时记录缺口，不启动独立深度调研流程。
4. 形成少量不同的解释或候选方案。
5. 寻找重复工作、反例和更简单的替代解释。
6. 比较、修改，输出建议和最小验证办法。
7. 保存本轮变化，关联回原问题。

产物：难点分析、候选假设或方案、依据、风险、建议验证步骤。
可以没有合格候选，也可以建议停止某个方向。
不要求每轮强制生成固定数量的 idea。
保留查找已有工作、核对原文和寻找反证的步骤；不要求穷尽整个领域或交付完整综述报告。
外部补查只使用实现阶段明确接入的来源，缺少访问能力时如实标明范围。

### E. 结果与反馈回流

所有研究结束后，都要回答“这次研究让项目发生了什么变化”。

- 新发现作为带出处的材料进入项目。
- 候选 idea 以待讨论或待验证状态保存。
- 用户采纳、修改、否决和理由关联到原候选。
- 实验结果关联原假设，记录支持、不支持或无法判断。
- 未完成事项回到问题清单。
- 已明确的项目决定进入决策记录。
- 新材料影响旧结论时，保留修订关系和原因。

研究报告、项目概览、问题状态应引用同一组事实记录，避免各自形成不一致的“项目真相”。
私有研究的结果默认回到个人记录；只有明确发布且来源允许共享的内容才回到项目共享记录。

### F. 用户身份、权限与共享

这是全框架的基础能力，需先于研究功能实现，不作为最后追加的功能。

**MVP 的三个内容范围：**

| 范围 | 允许内容 | 可见者 |
| --- | --- | --- |
| 个人私有 | 私聊、个人偏好、未公开经验、私有笔记、私有研究与候选 | 记录所属用户 |
| 项目共享 | 明确分享的项目背景、问题、进展、决定、实验和研究结论 | 当前项目成员 |
| 公共资料 | 可公开获取的论文原始元数据、摘要和正文（实际可用范围内） | 获准使用公共资料库的用户 |

公共论文的内容可以复用；谁阅读过、个人批注、订阅条件和基于私有信息得出的判断不因此变成公共。
MVP 不建立默认全用户共享的个人记忆池，也不默认把项目共享等同于对所有用户公开。

**身份与会话：**

- 每个用户有可信、稳定的身份；身份来自实际登录或可信接入渠道，不能让模型或用户填写一个 ID 就冒充别人。
- 每个内部用户固定绑定专用 profile；同一用户可以绑定多个渠道账号，昵称相同不代表同一用户。
- 每次访问都绑定用户、当前项目和会话；请求参数中的资源 ID 不能替代权限检查。
- MVP 每个会话归属于一个用户和一个项目。切换项目建立独立会话，不沿用另一项目的私有上下文。
- 会话持久化和恢复复用 Hermes 原生能力，插件检查用户、profile 和项目绑定，不另建平行聊天存储。
- 多个会话可以读取同一个项目共享记录，但不直接读取其他成员的私聊历史。
- 群聊和多人共同编辑同一会话不纳入 MVP；以后接入时需要独立定义会话参与者与可见范围。

**读取与执行：**

- 当前项目视图 = 当前项目共享内容 + 当前用户在该项目的私有内容 + 可访问的公共资料。
- 未获权限的内容不能进入检索结果、摘要、模型上下文或研究执行者输入；不能依赖模型看到后自觉不说。
- 检索、原文读取、附件、报告下载、历史任务、日志和缓存都遵守同一范围；更换条目 ID 也不能越权。
- 缓存的上下文、对话压缩摘要、临时文件和研究工作区不能串用其他用户的内容。
- 用户退出项目后，新的请求、任务读取和结果交付按最新成员关系检查；已合法获得的副本不能承诺远程收回。
- 如果 Agent 可以使用文件、终端或外部资料凭据，执行资源也必须限制到其被授权的范围。仅给记录加标签，无法约束可任意读共享磁盘的执行者。
- 这些边界由运行系统和业务访问层落实；Skill / 提示词只能辅助，不能充当权限机制。

**写入与分享：**

- 私聊与个人研究默认私有；在明确的项目共享任务中产生、且输入范围允许共享的记录可直接写入项目共享范围。
- 用户可明确要求将自己的内容分享给项目；MVP 共享给整个项目成员，指定部分成员共享留到后续。
- 用户只能修改自己有权修改的内容。MVP 采用简单的项目所有者 / 成员关系，共享记录保留作者和修改历史，不默认允许覆盖别人的决定或实验结论。
- 管理项目成员或运行系统，不自动等于可以读取成员个人记忆；特殊运维访问需另行明确，不默认为产品权限。
- 研究使用了个人私有材料时，生成的报告、摘要、idea 和关联关系默认继承这些限制。
- 混合使用公共与私有材料的结果不能直接写入共享记忆。分享时应取得相关资料所有者的授权，或仅用允许共享的材料重新生成并检查。
- 不能只删除姓名或引用链接，就宣称私有材料派生的结论已经可以共享。
- 分享、撤回和成员变更保留记录。撤回后停止新的共享读取，并处理由它派生的可见摘要和缓存；已交付的副本无法保证收回。

**后台任务：**

- 每个任务必须有明确的发起身份、所属项目、资料范围、输出范围和结果接收者。
- 项目级每日任务只使用项目共享设置及允许访问的公共资料，不能借用某个成员的个人记忆。
- 项目任务由 research-service profile 统一执行，一个项目维护一份拉取任务，不随用户 profile 数量复制。
- 个人订阅或个人自动研究作为该用户的私有任务，结果不自动进入项目共享报告。
- 问题探索的子步骤沿用原任务的权限，不能因为转交另一个研究执行者而扩大访问范围。
- 执行与交付时重新检查权限；成员退出或资料权限变化后，不能继续按旧授权读取和发送结果。

## 5. 三条主流程

### 流程一：日常项目对话

    用户提问或报告进展
      → 确认身份、项目、会话归属和本次可见范围
      → 读取项目共享概览和该用户可见的相关问题
      → 按需查看具体记录与依据
      → 回答或讨论
      → 记录有实质变化的进展、决定、问题和经验
      → 按内容范围更新个人视图或项目共享概览

记录实质信息，不把所有闲聊自动当作项目结论。
记录“已完成”需要有用户报告或实际执行依据；计划执行与已经执行分开。

### 流程二：主动研究

    用户针对具体难点发起问题探索
      → 确认用户权限、输入范围和输出范围
      → 明确问题、范围和预期产物
      → 建立本次任务记录
      → 获取项目背景与相关历史
      → 执行对应研究流程
      → 保存报告、依据、候选和未完成项
      → 默认回到个人研究记录；共享任务按授权范围回流项目
      → 用户继续反馈或验证

范围清楚时直接开始，不为已有信息反复提问。
关键目标缺失时先澄清；部分资料不可用时明确缺口，不能假装完成全部调查。

### 流程三：每日更新与可选自动研究

    到达设定时间
      → 加载该任务的项目 / 个人身份与资料范围
      → 拉取和筛选新论文
      → 保存本次更新记录并关联项目问题
      → 检查自动研究设置
          ├─ 未启用：结束
          └─ 已启用，且本批资料匹配明确指定的问题：
                按相同权限建立问题探索任务 → 保存结果 → 回流对应范围

MVP 自动触发采用简单、可说明的规则：用户指定可自动研究的问题，且有匹配的新增材料。
触发规则、每轮上限和研究预算需要显式配置；同一批更新重跑不能重复启动同一个研究任务。
第一版不让 Agent 自主扩大研究方向或无限连续研究。

## 6. 各模块共享的最小记录

这里只确定概念和关联，不规定数据库表或文件格式。

| 记录 | 作用 | 主要关联 |
| --- | --- | --- |
| 用户与成员关系 | 可信身份、加入项目和共享访问边界 | 会话、个人记录、项目权限 |
| 会话 | 独立对话历史、所属用户和项目 | 当次上下文、任务、记录来源 |
| 项目 | 目标、约束、概览和进展 | 所有项目记录 |
| 问题 | 待解决难点和已尝试方案 | 资料、研究、idea、实验、决定 |
| 资料 | 论文、本地文档、个人经验及出处 | 问题和研究结果 |
| 更新批次 | 某次论文更新的范围与结果 | 新资料、关联问题、自动研究任务 |
| 研究任务 | 问题探索的过程与产物 | 输入、范围、来源、结果、未完成项 |
| 候选 idea | 假设、方法、依据与验证建议 | 原问题、产生它的研究、用户反馈 |
| 实验 / 尝试 | 做了什么、条件和结果 | 问题、idea、结论 |
| 决策与反馈 | 用户选择、理由和后续评价 | 对应方案、问题和研究 |

研究任务状态至少区分：进行中、已完成、部分完成、待补充、失败、取消。
“已完成”仅指本次范围内的任务完成，不等于 idea 有效、问题解决或新颖性得到证明。
每次任务保留目的、输入范围、时间、实际参考来源、结果和未完成项，支持追溯与继续研究。
内容记录同时保留所属用户 / 项目、可见范围、作者、修改历史和派生来源。
身份、可见范围与资料继承关系需要在第一版就明确，具体存储结构后续再定。

## 7. 实现阶段与验收

以下为功能阶段概览；具体开发顺序、profile 部署、渠道路由与完成标准以 IMPLEMENTATION_PLAN.md 的 M0–M5 为准。

### 阶段 0：先建立多用户与共享边界

交付：

- 两个可信用户身份、一个共享项目、清晰的成员关系。
- 独立会话与个人记忆；个人私有 / 项目共享 / 公共资料三种范围。
- 在信息进入模型之前检查权限，约束资料访问、缓存、运行工作区和结果交付。
- 明确的分享入口、派生内容范围，以及成员变更的处理。

验收：

- A 和 B 的私聊内容互不可见；同一项目共享记录双方可见。
- A 的个人经验可影响 A 的研究，但 B 无法从搜索、报告、摘要或项目概览中获得它。
- A 明确分享一条允许共享的结论后，B 的新会话可使用该结论，但不能读取 A 的整段私聊。
- 修改请求中的用户、项目或条目 ID，不能读取或更改无权访问的记录。
- A 的私有资料进入一份报告后，这份报告不能直接进入 B 的共享视图。
- 顺序或并发运行 A、B 的任务，不会因复用会话、缓存、日志或文件路径而互相泄漏。
- 权限撤销后，在途任务的后续读取和交付遵守新权限。

这一阶段不过关，不接入共享资料开展真实多用户研究。

### 阶段 1：先让 Agent 了解一个真实项目

交付：

- 项目初始化和信息边界。
- 项目概览、问题清单、进展、决策与经验的维护。
- 日常对话能查询并记录实质更新。

验收：

- 输入项目背景、已有工作和一个失败案例。
- 换新会话后询问“我们做过什么、为什么失败、目前卡在哪里”。
- 回答能够关联具体记录；没有记录的信息明确说不知道。
- 对话中报告一项真实进展后，新会话能了解该变化。
- A、B 分别重开会话时，能看到共同的项目背景，以及各自获准访问的个人记录。

这一阶段是其余模块的共同基础。

### 阶段 2：每日论文更新

交付：

- 一个真实论文来源及项目相关性筛选。
- 固定时间执行、手动补跑、去重和执行结果记录。
- 新论文可进入项目问答和后续研究。

验收：

- 完成一次真实拉取，并验证一次定时执行。
- 相同批次重跑不重复建资料。
- 来源不可用时显示失败；空更新显示无新增。
- 能回答“最近新增哪些论文，与哪些问题有关”。
- 项目级定时任务不读取个人私聊；个人订阅与个人批注不会出现在公共论文库或共享更新中。

拉取时间和研究课题由用户在启用前提供，实际定时任务届时再创建。

### 阶段 3：主动问题探索

交付：

- 回顾项目历史，分析特定难点。
- 检索和阅读相关材料，按需定向补查，产生、评审和修改候选。
- 输出验证建议并记录人工反馈。

验收：

- 给定真实难点，结果能利用已有尝试和失败经验。
- 候选能解释相对已检索工作的差异，并给出最小验证办法。
- 用户否决或补充实验结果后，下一次探索能检索并利用这条反馈。
- 没有值得推荐的候选时，能说明原因。
- 能查看实际依据与本轮检查范围；资料不足时保留缺口，不给出假确定结论。
- 基于个人经验产生的 idea 保持相应可见范围；共享前完成授权或用共享资料重新研究。

### 阶段 4：自动触发与完整回流验收

交付：

- 每日更新后，按明确规则可选触发指定问题探索。
- 任务状态、失败记录、重复触发控制和项目概览同步。
- 一条覆盖项目记忆、论文更新、问题探索与权限边界的人工演示流程。

验收：

- 在自动研究关闭时，更新论文不会启动研究。
- 开启指定问题的自动研究后，匹配的新资料能启动一次任务。
- 同一批更新重跑不重复启动任务。
- 自动研究后的报告和候选能够在新会话中查询。
- 研究失败不抹掉已成功拉取的论文，也不被报告为研究完成。
- 自动任务与手动任务使用同一套权限规则，结果只交付给当时仍有权限的接收者。

开发时按以上顺序推进；每一阶段先验证真实行为，再进入下一阶段。
性能、召回率和 idea 质量可以后续改善，模块之间的信息传递与结果回流必须先完整。

## 8. MVP 最终验收故事

1. A 和 B 加入同一个项目，各自开启独立会话。
2. A 描述项目及当前难点，将明确共享的背景和实验记录放入项目，同时保留一条个人私有经验；Agent 整理对应范围的记录。
3. 每日任务抓取与课题有关的新论文，留下本轮更新记录。
4. 用户询问项目进展和最近论文的相关性，Agent 能结合项目记录回答。
5. 用户要求针对原难点进行问题探索，Agent 回顾项目历史，检索和阅读相关论文，提出有依据的候选与验证建议。
6. 用户否决一个候选，说明原因，或提供一次实际实验结果。
7. 下一次会话 / 研究能使用有权访问的反馈；共享问题状态和项目概览保持一致，B 不会获得 A 的私有经验或个人研究。
8. 启用可选自动研究后，重复一次每日更新到研究结果回流的流程。
9. A 将一条可以分享的个人结论发布到项目后，B 能利用该结论，但仍不能访问 A 的私聊和未分享材料。

以上故事跑通，即达到第一版功能目标；不以生成多少 idea、写出多长报告作为验收标准。

## 9. 使用与开发约定

- 使用现有 Hermes；源码独立维护，通过已验证的本地链接方式接入。
- 各用户 profile 和服务 profile 分别通过 Hermes 插件机制部署启用同一版本，不假定它们自动继承默认 profile 的插件。
- 不为开发实验另建 Hermes HOME 或复制运行环境；正式多用户的会话、数据和执行资源必须按上述权限边界隔离，部署方式实现时确定。
- 沿用人工操作验收的偏好，不为规划搭建额外测试平台。
- 实现阶段需要对关键持久化和重复执行行为做必要检查，但不先堆测试脚手架。
- 源码的目标组织见 PROJECT_STRUCTURE.md，按开发阶段逐步创建；资料和运行记录的底层保存格式在对应模块实现前确定。
- Windows 开发，Linux 迁移时保留项目语义和记录，替换本机路径与启动配置。
- 具体模型、框架集成、检索引擎、数据格式和执行预算尚未选定。
- 不能预设 Hermes 的会话分离就覆盖了资料、长期记忆和执行权限；实现接入时逐项核对其实际加载和访问路径。

## 10. 开始实现前的最少输入

先从用户处取得一个真实项目的：

1. 名称、研究方向和希望解决的问题。
2. 已有资料，以及至少一项历史尝试 / 实验或个人经验。
3. 当前资源约束与希望获得的研究产物。
4. 至少两个验证用户的身份来源、项目成员关系，以及哪些背景资料可以共享、哪些必须私有。

在实现论文更新时再确定关键词、时间窗口、固定执行时间和时区。
在启用自动研究时再确定允许研究的问题、触发条件和预算。
不要求用户一开始写完所有细节；已知信息先建立项目，缺失部分明确记录并逐步补充。
